# Dendro 置信度可信度评估（2026-11-27）

> 评估对象：`cambium.dendro` 的**项目置信度**（`dendro check / gen / query`）与**补丁置信度**（`dendro patch / merge`）。
> 代码位置以 `6fc55a3`（feat/sylva-brand）为准；行号均指该提交。
> 证据分三种，正文里逐条标明：**实测**（本机跑出来的）、**代码事实**（读源码看到的）、**推断**（由代码推出、没有单独验证）。

## 0. 结论

现在的分数是「结构性疑点的密度」：24 类疑点各有一个手填的整数权重，密度过一条饱和曲线变成 0–100。
它从设计起就声明「不是正确性证明」，这一点一直守住了。但要让读数**可信**，缺的不是再多几类检测器，
而是三件更根本的事：

1. **分数不稳定，且不稳定的方向是系统性的。** 同样的代码质量，仓库越大、分析覆盖越少、样本越小，
   读数越不可比——而且三种情况下都是朝着「看不出问题」的方向偏（§3 的 A1–A3）。
2. **罚分被实测精度接近 0 的类别主导。** 本机两个仓库上，「幻觉调用」占列出罚分的 14% / 39%，
   而它在本机的抽样是 22 条里 0 条真的是编造的 API（仓库自己早先的记录也是 20 条里 0 条）。（§3 的 B1）
3. **没有「这个分数凭什么可信」的度量回路。** 全仓没有带标注的数据、没有校准、没有回测；
   精度证据只有几段人工抽样的散文（10 条、20 条）。（§3 的 C）

最高杠杆的五件事，按先后顺序：

| # | 做什么 | 为什么排这里 |
|---|---|---|
| 1 | 分数改用**完整计数**算，截断只管展示 | 现在超过 400 条疑点后罚分封顶，仓库越大分越高——恰好违背不变量 128 想解决的问题 |
| 2 | 输出**分析覆盖度**，覆盖不足时读数必须带着覆盖度一起出现 | 本机没装 ast-grep，置信度一直跑在词法档，7 类疑点根本没查，分数却照常给 |
| 3 | 实测精度很低的类别**降为零罚分（只报告）**或大幅降权 | 一条假疑点扣 8 分，一条真的孤儿才扣 12 分 |
| 4 | 建立**标注 → 精度 → 权重**的回路 | 没有它，上面每一条都只是另一次手调 |
| 5 | 修掉§3.2 列出的确定性缺陷（重复计分、行号错、词表不一致等） | 便宜、无争议，且其中两条直接让输出说错话 |

## 1. 现状模型（代码事实）

- **疑点与权重**：`FlawKind` 24 类，权重表 `flawWeight`（`src/dendro/confidence.cj:146-173`）。
  自 2026-10-11（`2123880`）起没有任何权重改过。权重的依据是 5 篇论文的**一般性结论**
  （`docs/audit-2026-10-09.md:356-374`），不是对每一类检测器的验证。
- **分数**：`density = 罚分 / 文件数`，`score = 100·S / (S + density)`，`S = 20`
  （`confidence.cj:717-730`）。密度 20 得 50 分。
- **上限**：每文件每类 6 条（`CONF_MAX_PER_KIND_PER_FILE`）、全量 400 条（`CONF_MAX_FINDINGS`）
  （`confidence.cj:254-256`）。**罚分是在截断之后对 `findings` 求和的**（`confidence.cj:584-591` 与 `:680-683`）。
- **语法树**：外部 `ast-grep`，覆盖 9 种语言里的 8 种（仓颉没有 tree-sitter 语法）
  （`src/dendro/confidence_ast.cj:69-81`）。不可用时降级为词法，**有 7 类疑点整类消失**：
  `swallowed-error`、`duplicate-body`、`unused-variable`、`empty-type`、`god-class`、`lock-imbalance`、`lock-unknown-call`；
  降级说明里只提了前两类（`confidence.cj:510-521`）。
- **补丁置信度**：S1–S10 十路信号取**等权平均**（`src/dendro/patchconf.cj:518-525`）；
  Layer 3 合并是对各实体的置信度再取一次平均，**Layer 1 的总分不参与**（`src/dendro/patchconf_render.cj:221`）。

## 3. 可信度问题清单

### 3.1 分数本身（A）

**A1 · 超过 400 条后，仓库越大分越高。**（代码事实 + 实测）
罚分在截断后求和，上限约为 400 × 12 = 4,800；分母却是全部文件数。4,000 个文件的仓库哪怕处处是孤儿符号，
分数也 ≥ 94。不变量 128（「归一化指标的分母必须与被归一的量同阶增长」）正是为了消除规模相关性，
这个上限把它在大仓库上重新引入了，方向还反过来。本机两个仓都撞了上限：按全量算是 21–29 和 46–60，报告给的是 34 和 67。
每文件每类的 6 条上限同理：热点文件被系统性低估。注释说「超出时计数汇总为一条」（`confidence.cj:253`），
实现只有一个布尔值 `cappedKind`，超出多少、罚分多少都没给。

**A2 · 分析越少，分越高。**（代码事实）
词法档下 7 类疑点不产生任何罚分，分数却照常输出。本机就是这种情况：用户看到的每一个置信度数字都是词法档的。
降级说明只在 `astNote` 里，而且少说了一半（只提「吞错与重复体」）。此外：
- `ast-grep` 只在 4 个固定路径里找，不查 `PATH`（`confidence_ast.cj:34-45`）；`CAMBIUM_AST_GREP` 环境变量没有任何文档提到。
  用 cargo / npm 装的 `ast-grep` 引擎看不到——装了也白装。
- 部分 `ast-grep` 批次失败时，那些文件既没有 AST 信号也不补词法信号（`confidence_detect.cj:631`，推断）。
- 图谱层自己还有 4,000 个文件、单文件 512 KB 的上限（`src/graph/build.cj:20-21`），置信度输出里不披露。

**A3 · 样本越小，读数越抖，却没有任何不确定度的表示。**（实测）
1 个文件的仓库里一条假疑点 = −20 分；1,000 个文件的仓库里同一条疑点 = −0.02 分。两者都显示成一个光秃秃的「51」。

**A4 · 同一个事实被重复计分。**（代码事实）
- 一个空的 `catch` 同时报 `stub-body`（12）和 `swallowed-error`（10）：一处问题 22 分（`confidence_detect.cj:325` 对所有节点都跑占位判定）。
  空类型同理（`stub-body` + `empty-type`）。
- 「函数很大」这一个事实会同时触发 `long-function`（4）、`deep-nesting`（4）、`high-complexity`（8）、`magic-number`（3）、
  `parameter-abuse`（6）：四类检测器高度相关，却各自独立扣分。
- 补丁置信度里 S1 与 S10 是同一个量（`resolvedRefs / totalRefs`，`patchconf.cj:479` 与 `:515`），进了两次平均。

**A5 · 阈值是台阶，不是坡。**（代码事实）
79 行的函数 0 分，81 行 4 分；圈复杂度 10 不报，11 报 8 分。紧挨着阈值的两侧读数不连续。

**A6 · 分母和上下文都不分。**（代码事实）
密度按「文件数」归一：加 100 个空文件就能把分数拉上去。测试、生成物、第三方代码与生产代码同权
（文件遍历只按目录名跳过 `vendor` / `build` 等，`build.cj:28-41`，没有生成物与测试文件的识别）。
图谱里有调用关系，但分数不用它：入口可达路径上的疑点与外围的疑点同权。

**A7 · 分数没有版本。**（代码事实）
权重与阈值改过四轮，输出里没有任何模型版本或权重指纹。两次读数不可比，趋势线也无从解释。

### 3.3 度量回路（C）

**C1 · 没有任何带标注的数据。**（代码事实）
全仓（不含构建产物）没有任何 oracle、标注集、基准或回测；提交历史里「校准 / 回测 / oracle / recall / precision /
ground truth」零命中。精度证据是三段人工抽样的散文：孤儿 10 条 6 真、幻觉调用 20 条 0 真、未使用 import 10 条 9 误（已修）。
没有逐条标签，换一次代码就得重抽。

**C2 · 测试钉的是「行为不变」，不是「结论正确」。**（代码事实）
约 50 条相关测试钉住了排序全序、上限披露、JSON 键集、降级说明、分层——都是契约，都对。
但没有任何测试断言过某份夹具的绝对分数、任何一路补丁信号的取值、任何合并常数。
唯一的变异测试（`scripts/nc-*.sh`）在改名后已经失效（B20）。

**C3 · 审计清单里两项一直没勾。**（代码事实）
`docs/audit-2026-10-09.md:378-382`：「置信度模型重设计：六维度 → 可靠性/设计哲学双轴评分」「引擎自身验证」。

## 4. 优化路线

每一条都带验收判据。顺序就是优先级：0 不依赖任何数据，1 是在攒数据，2 才动模型。

### 阶段 0 · 止血（不依赖数据，改动小）

1. **分数用完整计数**：罚分在截断**之前**求和；400 条只限制展示清单。输出补 `penaltyTotal`、`findingsTotal`。
   - 判据：同一批疑点，文件数 ×10、疑点数 ×10 时分数不变（现有 `testScoreIsSizeInvariantAndMonotone` 的端到端版）；
     超过 400 条时 `score` 与「把上限调到无穷大」时逐位相等。
2. **覆盖度进输出、进界面**：`coverage = { astFiles, lexicalFiles, analyzedFiles, missingKinds: [...] }`；
   词法档时顶层给 `degraded: true`。降级说明列全 7 类。客户端在分数旁常驻显示「词法档 · 覆盖 8/9 语言」。
   - 判据：现有「降级说明进每个出口」的测试扩到 `coverage` 键；`missingKinds` 与代码里「AST only」的类别集合逐项相等（源码守卫）。
3. **精度低的类别停止扣分**：`unresolved-call`、`dead-branch` 先降为「只报告不扣分」（`weight = 0`，仍带证据列出），
   并在 finding 上加 `precision: "low"`。修好 B2 之后再恢复 `dead-branch` 的权重。
   - 判据：权重表里为 0 的类别必须同时出现在「只报告」名单里（源码守卫）；本机 deepDolphin 整仓的罚分构成里 `unresolved-call` 归零。
4. **消掉重复计分**：空的 `catch` 只报 `swallowed-error`；空类型只报 `empty-type`；补丁信号去掉 S10（或让 S10 真的去量别的东西）。
   - 判据：同一夹具里一个空 `catch` 的罚分恰好是 10。
5. **修 §3.2 的 B2–B19**，每条配一条判据；B15 统一裁决词，并对未知裁决词报错而不是静默放过。
6. **补上 `ast-grep` 的 `PATH` 查找**，把 `CAMBIUM_AST_GREP` 写进 README；修好两个负控脚本的路径（B20）。
7. **分数带版本**：输出加 `modelVersion`（权重表 + 阈值的指纹），`confidence.db` 的 `meta` 带时间戳与索引版本。

### 阶段 1 · 度量回路（在攒数据）

8. **裁决台账**：`dendro verdict`（或复用补丁那套 `agent.json`）记录人对疑点的裁决
   `true / false-positive / unsure`，键用（类别，文件，符号内容哈希）而不是行号，挪一行不丢。
   - 判据：同一疑点挪动行号后台账仍然命中；引擎不写仓库（台账在 store 里）。
9. **类别精度进报告**：每类给出已复核条数与命中率，例如「`orphan` 9/10 · `unresolved-call` 0/22 · 未复核」，
   客户端在按类别展开时显示。**没有样本就写「未复核」，不许留空让人以为可信。**
   - 判据：报告里的精度与台账逐类相等；没有台账时全部显示「未复核」。
10. **种子缺陷基准（进 CI）**：一个小型多语言夹具集，按类别 × 语言 × 路径（AST / 词法）注入已知写法，量检出率；
    同时保证干净样本零报告。
    - 判据：每类的检出率与误报率是一张表，任何检测器改动都要重跑；表进文档。
11. **历史回测**（需要 git）：对每个文件取「t 时刻的疑点」对「之后 90 天内是否被修复类提交改过」，
    出 AUC、按分数档的命中提升、校准表。这是权重的经验依据。
    - 判据：在 Cambium 与 deepDolphin 两个仓上跑出第一张校准表，写进本文档的「基线」一节。

### 阶段 2 · 模型（数据够了再动）

12. **权重按数据重定**：用台账与回测拟合（逻辑回归，或以类别精度为先验的朴素贝叶斯），
    输出带校准曲线的「含缺陷可能性」，旧的 0–100 作为派生视图保留。`modelVersion` 随之递增。
    - 判据：留出集上的 Brier 分数与校准误差写进文档；新旧分数的秩相关给出，便于对照。
13. **聚合方式**：按函数出分 → 按文件聚合 → 项目聚合，每一级用饱和函数；
    「函数很大」这一族（长 / 深 / 复杂 / 魔法数 / 参数多）合并为一组联合上限；
    同类同文件的罚分用对数式递减。密度改按**已分析的代码行数**归一，而不是文件数。
    - 判据：加 100 个空文件分数不变；一个 300 行的复杂函数的罚分有上界；同一个函数重复 20 次魔法数与 5 次的罚分之比小于 4。
14. **上下文加权**：测试 / 生成物 / 第三方 / 脚本单独出分，不进生产代码的分数；
    用图谱的可达性给疑点加权（入口可达路径上的更重，完全不可达的孤儿是确定的）；
    git 的改动频率与新近程度、是否被测试引用，作为附加信号。
    - 判据：只改测试文件不影响生产分数；可达性权重改变后，排序变化有据可查（每条 finding 带上它的权重来源）。
15. **小样本收缩**：`density = (penalty + k·prior) / (files + k)`，并随分数给出区间或「样本不足」。
    - 判据：1 个文件 1 条疑点的仓库不再得到一个和 1,000 文件仓库同样自信的数字。
16. **与 Layer 2 的融合**：确定性先验 + agent 裁决 → 带来源的终稿；agent 的精度先在标注集上量出来，再决定它的权重
    （现在的 ×0.9 是拍的）。引擎仍然不做 LLM 调用。

### 阶段 3 · 产品化

17. 每次提交的分数变化带归因（哪几条疑点进了、哪几条出了）；抑制注释 `// dendro:ignore <kind> <理由> [until 日期]`
    进台账而不是散落成误报；趋势图按 `modelVersion` 分段。

## 5. 不建议做的

- **在拿到标注数据之前再调权重、再加检测器。** 没有度量，每一次调整都是一次不可验证的手调；过去四轮权重表都是这样改的。
- **在没校准之前把分数说成「正确概率」。** 现在的 51 不是「51% 可能是对的」。
- **为了提高检出率去放宽阈值。** 本机数据说明问题在另一头：最吵的几类恰恰是假的。
- **让引擎调模型。** 红线不动：语义复核在上层 agent，引擎只出确定性信号与复核提示词。
